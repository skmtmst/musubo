## 1. 目的・効く目標・ライバルとの差

- 目的：Claude などの AI から musubo の数を読み、配信の下書きを作り、（選んだ時だけ）送る依頼を出せる。何をされたかは全部記録に残り、止めるボタンは 1 か所。
- 効く目標：③ 作り込める（AI で運用を自動化）・① 引き継ぎ（記録が残る）・② 直感的（3 段階の権限）。
- ライバルとの差：エルメは読み取りから設定の操作まで広げた。musubo は ①既定は**読むだけ** ②送るは選んだ時だけ・必ず人の承認待ちに入る ③範囲外の依頼も「断った」と記録 ④止めるのは 1 か所。

### 2-2. できることの 3 段階（言い方をそろえる）

| 段 | 画面の言葉 | できる | できない |

### 2-3-A. MCP が作った一斉配信の承認後送信（2026-11-19 暫定案・再確認待ち）

**実装・migration・検証送信・本番有効化は未承認。** この節は、まさとさんの暫定案を正本へ反映し、改訂版の再確認を受けるためのもの。対象は MCP が作る一斉配信の下書きに限る。受信箱の1対1返信・Q&A の自動応答は対象外。AI は送信の依頼までで、承認や直接送信はできない。人数が少なくても必ず人の承認を通す。

1. **承認する人**：指定された対象店舗に操作権限のある、有効なオーナー・管理者だけ。個別権限のあるスタッフも、この機能の承認者には含めない。MCP 接続を作った本人が条件を満たす場合は、自分の AI の依頼も承認できる。本人確認には既存の重要操作の基準を使う。代理ログイン・閲覧のみ・対象店舗の権限がない人は承認できない。
2. **承認期限と予定時刻**：依頼から24時間を当初は固定し、期限ちょうど以降の承認は拒否する。未承認のまま予約時刻を過ぎたものは送らず、予約し直して再依頼する。予約時刻を過ぎた依頼は承認できない状態とし、24時間内でも承認済みにしない。承認済みの予約が承認期限後の時刻に届くこと自体は妨げない。
3. **宛先の固定**：承認時に本文・版・店舗・対象条件・送信予定と宛先集合を固定する。送信直前は同意取消・ブロック・所属変更などで除くことだけ許す。増えた宛先を後から足さず、本文や対象を変える場合は再承認する。件数だけが同じでも別の人に入れ替わってはならない。
4. **接続停止**：AI 接続が停止・期限切れになった後の未送信分は止める。送信途中は新しい送信を始めず、送信済み・結果不明の分は取り消したと表示しない。再開は状態と権限を確認し、再依頼・再承認する。
5. **お知らせ**：承認承認期限（依頼から24時間）の2時間前と期限切れに、それぞれ承認できる人へ管理画面で1回ずつ知らせる。予約時刻を過ぎた依頼は再依頼が必要と示し、その時点ですでに承認できなくなった依頼に古い予告を出さない。予約時刻による停止のお知らせの方式は再確認する。Push は本人の設定と有効な購読がある場合だけ。承認できる人が0人なら送信を止め、管理者が対応できる状態にする。承認済み・取消済みへの古い予告、定期処理の重複で同じお知らせを増やさない。画面内の通知を正本とし、Push の端末到達を保証したと見せない。
6. **二重送信と結果不明**：承認と送信予定は一体で確定し、同じ依頼・同じ宛先の重複送信を防ぐ。送信した可能性がある結果不明分は自動再送しない。対象店舗の権限者が送信台帳の証拠を見て照合し、再送の要否を判断する。判断できる人は承認できる人と同じ owner/admin とする案を再確認する。
7. **環境と記録**：実装は機能をオフで始める。環境フラグの変更は運営管理者が管理し、本人確認・変更者・時刻・理由を記録する案とする。検証環境ではサーバ側で `test_recipients` に登録された対象店舗の相手だけに送る。空・不正・判定不能なら送らない。本番への有効化は別途承認する。承認・送信・通知の監査記録は G9 の既存方針に合わせ **1年を仮案**とし、保存期間と個人情報の削除は専門家・運営が確定するまで未決とする。宛先の固定記録の保存範囲と削除時期も別途確定する。

送信開始前に接続・店舗・権限・版・宛先・同意と送信枠をサーバで再確認する。承認・取消・期限切れの同時操作は片方だけ確定し、処理途中で停止しても通知・送信予定を取りこぼさない。詳細の移行・復旧案は実装前に設計レビューを通す。

## 3. データと API の形（案・Codex）

- **承認後送信の設計案・未実装**：現在の `725_broadcast_execution_contexts.sql` は実行モードを simulation に限定し、実送信の台帳への記録もトリガーで止めている。未採番の migration 草案では既存の模擬データと既定値を保ち、承認済みの対象配信だけを例外とする。制約やトリガーを単に外して、模擬配信や通常の未承認配信まで送れるようにしない。新旧 Worker・DB の組み合わせと失敗からの復旧を確認してから採番・適用を別途判断する。
- 依頼ごとの ID・本文と対象の版・宛先集合・期限・承認者・実行環境を結び付け、承認・取消・期限切れは条件付きで確定する。承認と送信予定、期限切れと通知予定はそれぞれ一体で記録し、再実行・定期処理の並走で二重送信や通知の欠落を起こさない。即時・予約・再開・再送のすべての送信口で権限と停止を再確認する。
- 表（マイグレーション・小）：
  - `mcp_connections`：`id`・`organization_id`・`name`・`level`（read/draft/send_request）・`account_ids_json`・`key_hash`・`key_prefix`・`previous_key_hash`・`previous_key_expires_at`・`expires_at`・`status`（active/stopped/expired）・`created_by`・`stopped_by`・`last_used_at`。
  - `mcp_call_logs`：`id`・`connection_id`・`tool`・`account_id`・`result`（ok/refused/error/rate_limited）・`refused_reason`・`target_type`・`target_id`・`summary`（個人情報なし）・`at`。
- 口：
  - 管理画面：`GET/POST /api/mcp-connections`（POST は step-up・鍵は応答に 1 回だけ）・`POST /api/mcp-connections/:id/stop`・`POST /api/mcp-connections/:id/rotate`・`GET /api/mcp-connections/logs?connectionId&result&cursor`。
  - MCP：`POST /mcp`（Worker 上の MCP サーバー・Streamable HTTP・`Authorization: Bearer`）。道具は 2-4。各道具は段と使えるアカウントを確かめ、外れたら断って記録。送る依頼は今の承認（broadcast-approvals）に「依頼者＝AI の接続（作った人）」で入る。
  - 下書きに `created_via`（mcp）と接続 ID。承認の画面に「AI の接続『○○』からの依頼」。

## 6. 決まっていない所（B-337 おすすめ）

- 2-3 の既存の「決定：おすすめ」に加え、2-3-A の暫定案は改訂版の再確認待ち。記録の具体的な保持・削除、環境フラグの運用手順、宛先集合の保存上限・移行手順は実装前に確定する。
- AI の依頼を作った本人が承認してよいか：対象店舗で操作権限のある owner/admin ならよい（AI が作った物を人が確かめる形のため）。ただし本人確認つき。→ 決定：おすすめ。
- 統括の接続・予約や友だちのタグを書く道具・OAuth：次の段。→ 決定：おすすめ。
