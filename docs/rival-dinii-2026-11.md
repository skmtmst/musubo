# ダイニー（dinii）比較調査と将来像メモ

- 調査基準日: 2026-11-26
- 対象: 株式会社ダイニー（dinii）の公開サービス一式、および musubo の現行機能・要件
- 想定利用者: オーナー、共同開発者、プロダクト企画・設計担当
- 目的: 飲食店の「レジ〜モバイルオーダー〜会員化〜再来店」の将来像を計画へ入れるための比較材料を作る。**この文書は計画用の調査であり、実装や仕様確定は行わない**
- 関連資料: [Lステップ・Liny 画面／裏側挙動の再調査と実装仕様](lstep-liny-screen-behavior-research-2026-08.md)、[Lステップで確認できなかった箇所と、置いた想定](lstep-unverified-assumptions.md)、[ライバルに対抗する機能一覧](v8-requirements/gap-features/README.md)

## 1. 結論

ダイニーは単なる「テーブルからスマホで注文できるツール」ではない。**自社POSレジを土台に、モバイルオーダー・決済・予約台帳・LINE会員管理（CRM）・集客・勤怠・経営管理までを一本でつないだ飲食店特化の統合基盤（All in One Restaurant Cloud.）**である。`B`

ダイニーの一番強い点は、次の循環が「お客さまの普通の注文」だけで自動的に回る構造にある。

```text
来店・卓上QRを読み取る
  → LINEミニアプリで自動会員化＋注文（誰が・いつ・何を食べたかを記録）
  → 店内ハンディに過去履歴が出て接客に使える
  → セルフ決済またはPOS会計で自動消し込み・退店（空席を予約台帳へ即反映）
  → 翌日に自動アンケート（QSCスコア化・口コミ依頼）
  → 注文履歴・経過日数で自動LINE配信＆売上効果を測定
  → 再来店（会員ランクアップ・友達紹介の計測）
```

一方、musubo の現在地は「LINE CRM・配信・フォーム・予約（飲食の席予約・来店スタンプ・予約メール取込・Googleビジネス・Instagram連携・デリバリー受注の受け皿を含む）」が強い一方、**店内モバイルオーダー・自社POSレジ・店舗決済端末・メニューごとの喫食データ連携は持っていない**。`C`

したがって、musubo が将来この領域を取り込む場合、**いきなり自社POSレジや決済端末から作るのではなく、「①他社POS（スマレジ・Airレジ等）からの会計・喫食データ取込 → ②LIFFを使った軽いモバイルオーダー／店頭QRチェックイン → ③必要なら自社会計・POSの要否を判断」の順**で段階的に進めるのが現実的である。

## 5. musubo が将来取り込むなら：何を・どの順で

ダイニーは資金・ハードウェア・現地設置・365日店舗サポート・決済審査まで抱える「飲食店OS」の戦い方をしており、musubo が正面から自社POSレジ・店頭決済端末・勤怠まで全部作り直すのは開発・サポート両面の負担が過大である。

一方で、**「すでにスマレジ・Airレジ・Square等を使っている店が、レジを買い替えずにダイニー級のLINE会員化・再来店自動化・モバイルオーダーを手に入れられる」**立ち位置は、ダイニーが自社POS前提で囲い込むほど musubo にとって明確な差別化になる。

取り込むなら次の4段階で進めるのが無理がない。

### 第1段階（最優先・ハード不要）：予約台帳×LINE×口コミの「循環」を閉じる

今の musubo の資産（飲食融合1〜4・来店スタンプQR・回答フォーム・Googleビジネス連携・G5 RFM/ランク）をつなぐだけで、ダイニーの「繁盛店サイクル」の半分近くをレジなしで再現できる。

1. **卓上QRチェックイン（非予約の飛び込み客を会員化）**: 既存の店頭QR来店スタンプを「テーブル着席時のチェックイン・クーポン受取」へ拡張し、予約なし客もLINE会員＋来店履歴に残す。
2. **空席検知→販促LINEの下書き／自動提案**: 予約盤の空き枠が多い曜日・時間帯を検知し、近隣・リピーターへ送る配信をワンクリックで提案（まずは人の確認付きで安全に開始）。
3. **退店後の簡単アンケート→QSC集計＋口コミ導線**: 既存の退店後フォローと5段階評価フォームを結び、店舗別の満足度推移をG7統括比較へ並べる。

### 第2段階（中優先・POS連携の入り口）：他社POSからの「会計・喫食データ取込」

レジを自作せず、既存POSから「いつ・誰が・いくら・何を食べたか」を受け取る口を作る。これにより **ダイニーの最大の武器である ID-POS 分析・喫食別セグメント配信・配信の売上効果測定** が musubo で実現できる。

1. **POS連携の共通受け皿（アダプタ構造）を設計**: どのPOSから来ても同じ形で保存できる「会計・明細イベント」と、LINE友だちとの紐付け方式（会員証バーコード／テーブルQRチェックイン／会計時QR）を定義する。
2. **第1号コネクタを1社に絞って接続**: 国内飲食でAPI公開があるクラウドPOS（例：スマレジ、Square等）から1社を選び、①会計金額・商品明細の取込、②配信→来店売上の帰属計算、③新規／リピーター別の人気メニュー（属性別ABC分析）を出す。
3. **会計完了→予約台帳の自動退店**: POSの会計イベントで予約盤の席を自動解放し、当日予約の取りこぼしを減らす（ダイニー×Resty連携と同じ価値）。

### 第3段階（要判断・飲食深掘り）：LIFF による軽量モバイルオーダー＋モバイル決済

第2段階でPOS連携の需要と運用負荷を見極めたうえで、店内注文へ踏み込む。

1. **LIFFモバイルオーダー（軽量版）**: 既存の飲食メニュー（写真・説明あり）とLIFF基盤を使い、テーブル固定QRから注文できる画面を作る。まずはテイクアウト・カフェ・小規模店など、キッチンプリンタ連携の複雑さが低い業態から始める（デリバリーフェーズ2のLINE自社注文と設計を共通化できる）。
2. **スマホ決済（セルフ会計）**: 既存の予約先払い（Stripe等）の仕組みを拡張し、注文後のオンライン決済に対応する。
3. **多言語・LINE非ユーザー対応**: LIFF外の通常Webブラウザ注文と自動翻訳は、インバウンド需要の高い店舗が増えてから追加する。

### 今回あえて取り込まない（後回し・非推奨）領域

- **自社POSレジ本体・店頭キャッシュレス端末・キッチンプリンタ保守**: ハードウェア調達、オフライン動作、インボイス印字、365日現地・電話サポートが必要になり、SaaS単体の軽さを失う。
- **勤怠・シフト・給与計算・受発注・FL経営管理**: 専門ツール（ジョブカン・マネーフォワード・インフォマート等）と競合し、musubo の「人と人を結ぶCRM」という軸から外れる。
- **推しエール・チップ機能**: 資金決済法・税務（給与／雑所得・消費税）の整理が必要になるため、優先度は低い。
