# musubo 新料金・利用開始フローの実装接続図

設計の正本は `musubo-pricing-v12-uiux-20261106.pen`。この文書は、設計済み画面を既存の課金実装に接続する際の境界を記録する。画面部品やメールの存在だけで、新料金を公開済みと判断しない。

## 確定した料金とタイミング

- 利用条件は運営が申込を承認する時点で、会社名と適用期限をサーバーで照合し、承認時の単価・無料期間をスナップショットとして固定する。特別割引はLINE基本料金だけに適用し、統括機能・友だち超過・追加連携枠には重ねない。
- 通常の無料期間は30日。条件ごとに日数または月数を設定でき、3か月などを扱う。起算日は最初のLINE有効化日。カード登録やログイン作成では起算しない。
- LINE基本料金は1個目¥5,900、2〜5個目は各¥7,900、6〜10個目は各¥6,900（税込・月額の初期値）。年払い10%割引はこの基本料金だけ。統括機能は2個以上で月額¥5,500、追加連携枠は1枠月額¥3,300、友だち超過は基準から1万人ごとに月額¥1,100（いずれも初期値）。オプションは年払い中も月次請求する。
- 各LINEでGoogleマイビジネスとInstagramをそれぞれ1個まで基本料金内で連携できる。追加枠は両サービスのうち多い方の連携数から1を引く。実店舗数を請求基準にしない。11個以上は個別見積もりへ進める。
- 有料利用中の追加は支払いが成功するまで新しいLINE・連携先だけを保留し、既存の利用は継続する。保留期限は7日。連携解除は即時、追加枠の減額は次の月次請求日から。支払済み期間を返金しない。
- 最後のLINEを0個にする場合、無料期間中は請求を始めず終了する。月払いは次の請求日、年払いは次の更新日での終了を初期選択にし、即時終了は別に選べる。会社アカウントと請求履歴を残す。再開時に新しい無料期間を与えない。
- 個別見積もりは最終単価と期限を保存し、期限内の同意を確定させる。同意済みなら見積もり期限後もカード登録を続けられる。未同意で期限切れなら再発行と再同意が必要。

## すでにコード化した部品

| 領域 | 主なコード | 接続時の注意 |
| --- | --- | --- |
| 料金・日割り・無料期間 | `packages/shared/src/musubo-pricing.ts` | 金額は整数円。年払いのLINE基本料金と月払いのオプションを分ける。 |
| 承認条件・会社制限 | `packages/shared/src/musubo-condition.ts` | 利用条件の変更を承認済み企業へ遡及させない。 |
| 個別見積もり | `packages/shared/src/musubo-individual-quote.ts`, `musubo-billing-flow.ts` | 最終単価を再割引せず、期限内の同意時刻を保持する。 |
| 追加連携枠 | `packages/shared/src/musubo-linked-addition.ts`, `musubo-linked-removal.ts` | 年払い利用中でも追加枠の日割り基準は月次期間。 |
| 顧客画面 | `apps/web/src/v8/onboarding/`, `apps/web/src/v8/hq/` の `musubo-*`・`linked-*`・`line-resumption*` | Penの各分岐を表示できる部品。サーバー確定の料金・日付だけを渡す。Stripeカード設定の戻り先 `/hq/onboarding/card` は登録状態を再照会する。 |
| 運営画面 | `apps/web/src/v8/ops/` の利用条件・個別見積もり部品 | 保存と送信は認可済みAPIへ接続する。 |
| メール | `apps/worker/src/services/` の `musubo-*mail.ts`, `quote-mail-design.ts`, `signup-mail-design.ts` | 検証済みのイベント後に送る。カード番号などは渡さない。 |
| 既存の有料請求失敗 | `apps/worker/src/services/billing-payment-failure.ts`, `billing-invoice-notifications.ts`, `apps/web/src/app/hq/billing/payment-recovery/page.tsx` | 失敗から7日間の猶予と通知は既存課金で動く。追加分失敗とは状態を分ける。 |

## 公開前に必要な接続

1. **DBと承認**：利用条件の版、承認時スナップショット、見積もり・同意、追加操作の保留、最初のLINE有効化日、各サービスの連携数を永続化する。新しい番号付きmigrationは `AGENTS.md` に従い番号ごとのオーナー承認後に作る。採番前にリモートと公開PRを再確認する。
2. **運営API**：利用条件の作成・版更新・停止、会社限定と期限の照合、申込承認、見積もり作成・再発行・送信前確認を認可付きで実装する。外部送信は送信対象と内容を確定させてから行う。
3. **顧客API**：承認済み条件の取得、料金プレビュー、見積もり同意、カード登録、追加・解除・最後のLINEの終了予約と取消、再開をサーバーの現在状態から処理する。画面の見積もり額や日付をそのまま請求根拠にしない。
4. **Stripe契約**：既存のStripe契約は旧 `light/standard/pro` とAPI `2024-06-20` を前提としている。新しい年払いのLINE基本料金と月次オプションを同じ契約で扱う方式を、Stripeの現行仕様で確定し、検証環境で請求・日割り・Webhook順序を再現する。追加分の請求失敗を通常の更新請求失敗と識別し、既存利用へ `past_due` を伝播させない。
5. **有効化ゲート**：最初のLINE接続と有効化が完了したときだけ無料期間を開始する。追加分は決済成功・必要な認証・接続確認のすべてが揃うまで有効化しない。重複Webhook・再試行・保留期限切れで二重請求や二重有効化をしない。
6. **画面の入口**：現在の新料金画面部品は大半がルート未接続。カード設定のStripe戻り先と既存請求失敗・復旧画面は接続済み。承認、ログイン、料金確認、カード設定に進む入口、既存LINEウィザード、運営コンソールを状態に応じてつなぐ。旧ウィザードの友だち数質問 `Q3. 友だちの数は50万人を超えていますか？` は、接続対象のLINEごとの大規模アカウント確認へ置き換えてから削除する。料金画面で尋ねる「既存LINEの合計」だけでは、LINEが複数ある場合に1個あたりの50万人超を判定できない。
7. **メール・通知**：Mail 01〜25の発火条件、再送の冪等性、受信者、送信失敗後の回復を接続する。送信処理を本番で有効にする段階では通常の外部通信承認ゲートを守る。
8. **検証と配備**：機能別の試験、型検査、ビルド、PenとのPC・スマートフォン照合、共有検証環境の順番待ちと完全SHA確認を行う。Codexの担当範囲はコミットまで。push・PR・統合・配備はリポジトリの司令塔運用に従う。

GoogleマイビジネスとInstagramの実際の複数アカウント接続およびGoogleマイビジネスへの複数投稿先選択は、依頼どおり別チャットの開発範囲とする。
